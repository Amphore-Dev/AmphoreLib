# Accessibility audit

Audit of every exported component against WCAG 2.2 AA and the WAI-ARIA Authoring Practices, done by reading the code and by running axe over each component's default and important states. Rules that keep applying live in [Guides/Accessibility](?path=/docs/guides-accessibility--docs).

**Severity.** Blocker: a task can't be done at all with a keyboard or a screen reader. Major: it can, but something essential is missing or misleading (no name, focus lost, state not conveyed). Minor: an inconvenience, or a best practice.

## What was and wasn't checked

| Check | Status |
|---|---|
| axe on every exported component, default state and open/error/disabled states (`tests/a11y/`) | Done, in the test suite. `tests/a11y/coverage.test.ts` fails if a new component has no axe assertion |
| Keyboard and focus behaviour, by reading the code, then with a regression test per fix | Done, in jsdom. Real browser behaviour not observed |
| Focus rings, by reading the stylesheets | Done. Not looked at in a browser |
| Color contrast | **Not run**: jsdom has no layout and resolves no color. Ratios below are computed from the theme's tokens. Storybook's a11y addon checks it per story |
| Target sizes | **Not measured**: no layout in jsdom. Suspects below, from the stylesheets |
| Manual pass with a screen reader (VoiceOver, NVDA, TalkBack) | **Not done.** Nothing here has been heard through one: the markup is verified, what's announced is not |

## Blockers

|---|---|---|

| Tabs | With a disabled tab selected, the only `tabindex="0"` sat on a disabled button: the whole tablist was skipped | Fixed |
| Tooltip | `useClick` swallowed Space on anything but a `<button>`: a checkbox nested in the trigger couldn't be toggled | Fixed |
| Popover | Portaled, it sat at the end of the document with no focus management: its content was out of reach | Fixed |
| FormRenderer | `<label htmlFor>` can't reach a combobox, or a group of controls: select, checkbox, radio, time, range, period and file fields had no name in every form | Fixed |
| Select | Searching: focus on the input, `role="combobox"` and `aria-activedescendant` on the box around it. Arrowing through options was silent | Fixed |

## Contrast

The default palette passes 4.5:1 for normal text, in both themes: every color's foreground on its fill, and its `-text` tone on a card, on its tint and on `ghostBg`, plus `ink` and `sub` on every surface. `src/theme/contrast.test.ts` keeps it that way. A color too light to carry text, such as `warning`, keeps a darker tone in its `warningText` token.

Two suspects remain, both on purpose:

| Theme | Foreground | Background | Ratio | Where |
|---|---|---|---|---|
| Light | `border` | white | 1.29 | Field outlines (3:1 for UI parts) |
| Dark | `border` | `card` | 1.36 | Field outlines |
| Light | `warning` | white | 1.98 | Outline borders, `Progress` and `Slider` fills |

## Target size suspects

Not changed here: a design matter. WCAG 2.5.8 asks for 24×24 px. `touch-target` already pads some of these on touch screens; none of it was measured.

| Component | Element |
|---|---|
| Badge, Select, ChipInput | Remove × (1.125em, about 13 px, outside touch screens) |
| Input, Select | Clear × |
| NumberInput | Steppers (half the field's height) |
| Checkbox, Radio | The box and circle alone, when used with no label |
| Tabs | Scroll arrows |
| TextArea | Resize corner |
| Table | "⋮" button in its 2rem column, `sm`/`xs` density |
| ToolBar | Icon buttons at their smallest |

## Checked, no defect found

Modal's focus trap and restore (FloatingFocusManager), now under test. Dropdown's arrow keys, Home/End, disabled items and Escape. Tabs' arrow keys and manual activation. Slider, a native range input. NumberInput's arrow keys, its steppers being out of the tab order on purpose. DatePicker's calendar keyboard (react-day-picker). Checkbox, Radio and Toggle, native inputs; Radio and Toggle rightly carry no `aria-invalid`. InfoMessage and InputErrorMessage live regions. Accordion's `aria-expanded`/`aria-controls`.
